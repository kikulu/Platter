# Platter 優化與改版建議

> 對象版本：`1.40.1`｜撰寫日期：2026-10-10｜性質：評估與建議。
>
> **`1.41.0` 更新**：§2.2（CI 加 `format:check`、測試缺套件時 skip；lockfile 仍待處理）、§2.3（`npm run check:docs`）、
> §2.8 的原子寫入與 `.bak`、§2.9 功能 A～D 已實作；其餘仍是建議。
> 已決定要做的項目請看 [`ROADMAP.md`](../ROADMAP.md)。
>
> 本文的「現況」都來自對程式碼與文件的實際檢查；標示「待確認」的是依 grep 或
> 結構推斷、沒有實機驗證的部分。

## 2. 建議（依優先順序）

### P0：可靠性與安全，先於新功能

#### 2.1 把「實機驗證」變成可重複的清單與冒煙測試

- 新增 `docs/MANUAL_QA.md`：把散落在 `BUILD_PLAN.md`「待手動驗證」與各版 `CHANGELOG`「已知限制」
  的項目整理成一份逐項勾選的清單（每項寫明步驟與預期結果）。
- 評估用 Playwright 的 Electron 支援＋ `xvfb` 在 CI 跑一支冒煙測試：啟動 App → 依序開啟
  各子視窗（知識庫、專案、文件庫、對話庫、設定、日誌、托盤）→ 斷言沒有 renderer 錯誤、
  主要元素存在。這不能取代人工驗證，但能抓到「DOM id 打錯、IPC 參數對不上」這類語法檢查
  抓不到的問題。
- 取捨：CI 時間變長、xvfb 下的視窗行為與真實桌面不同（托盤的顯示規則尤其無法在 xvfb 驗證）。

#### 2.2 依賴與 CI 一致

- 專案同時有 `yarn.lock`，但文件與 CI 都用 `npm install` 且沒有 `package-lock.json`，
  CI 因此每次解析到的版本可能不同。擇一：改用 `yarn install --frozen-lockfile`，或改成 npm
  並提交 `package-lock.json` 後用 `npm ci`。
- CI 觸發分支已在 `1.40.1` 補成 `main`／`master`；推送後請確認 Actions 真的有跑。
- CI 補跑 `npm run format:check`（目前只跑 lint 與測試）。
- 測試在缺少 `sql.js`／`mammoth` 時有 6 個失敗（本次整理的環境無法安裝套件，數字與
  `1.40.0` 的紀錄相同）。完整安裝後預期全過；建議在這些測試開頭檢查模組是否可載入，
  不行就明確 `skip` 並說明原因，避免「環境問題」與「真的壞了」混在一起。

#### 2.3 文件漂移的自動檢查

新增一支無依賴的 `scripts/check-docs.js`，掛進 `npm test`（或獨立的 `npm run check:docs`）：

- `package.json` 版本 = `CHANGELOG.md` 第一個版本標題 = 提示詞檔（`NEW_FEATURE_BUILD_PROMPT.md`、
  `FIX_EXISTING_FEATURE_PROMPT.md`）內寫的「目前版本」。
- 三語系 `renderer/locales/*.json` 鍵集合一致（現在靠人工比對）。
- 內建資料數量（提示詞、套餐、角色、專案範本）與 README／規格中的數字一致。
- README 文件索引連到的檔案都存在。

這一項成本低、直接消除本次發現的整類問題，建議最先做。

#### 2.4 內嵌第三方網站的安全加固

**已另做完整資安檢查，見 [`SECURITY_AUDIT_REPORT.md`](./SECURITY_AUDIT_REPORT.md)。** 先前這一節寫「沒有看到
`sandbox: true`」並不準確：Electron 20 之後渲染程序預設就啟用沙箱，這些視窗沒有關掉它，帳號視圖也沒有掛 preload。
真正的缺口是**所有視窗都沒有 `will-navigate`／`setWindowOpenHandler` 限制**（報告 H-1），以及備份匯入不驗證內容（M-1）。
修補順序與範圍以報告 §4 為準。

#### 2.5 Electron 升級

目前 `electron ^30.0.0`。Electron 只維護最新幾個主版本，30 已超出官方支援範圍，
安全修補不會再回補。建議在完成 §2.1 的冒煙測試之後升級到仍在支援的版本，並重點驗證：
`WebContentsView` 疊加與 `setBounds`、`session.fromPartition` 持久化、`electron-builder` 打包、
sql.js WASM 初始化。README 的 Electron 徽章已改回實際的 `^30`，升級後再同步更新。

### P1：維護成本與資料保護

#### 2.6 文件瘦身與分工

- `CHECKLIST.md` 已標示棄用且內容與現況不符，建議直接刪除（歷史在 git 裡）。
- `BUILD_PLAN.md` 凍結為歷史文件（Stage 1～16），檔頭加「已凍結，新功能不再往這裡加」，
  避免有人照舊慣例補 Stage 17。
- `CHANGELOG.md` 達 115KB：把 `1.1x`～`1.2x` 搬到 `docs/changelog-archive.md`，主檔只留近期版本
  與封存連結。
- `PROJECT_SPEC.md` 達 126KB：拆成 `docs/spec/01-…md` 等章節檔＋索引。這份文件同時是給 AI 讀的
  上下文，拆開後每次接續開發只需要載入相關章節。
- 三份 README 的功能總覽表有極長的儲存格（單格上千字）。建議表格只留一句話摘要，細節移到
  `docs/features/*.md`，三語 README 的同步成本會明顯下降。

#### 2.7 `renderer/project.js` 拆分（✅ `1.45.0` 已完成，改用多支一般 `<script>`，見 CHANGELOG）

2,216 行且持續成長（每個專案相關功能都往裡加）。比照 `1.17.0` 對 `main.js` 的做法，依功能拆成
任務清單、月曆、甘特圖、Issue、階段流程、關聯文件／簡報橋接等檔案，用 `<script type="module">`
載入（renderer 沒有打包工具，原生 ES module 即可，不需引入建置流程）。
取捨：純重構、沒有使用者可見的收益，所以只在動到該區域時順手做，並且獨立 commit。

#### 2.8 資料檔 schema 版本與集中式 migration（✅ `1.45.0` 已完成，見 `lib/migrations.js`；原子寫入部分已於 `1.41.0` 完成）

各資料檔目前沒有版本欄位，「舊資料正規化」散在各 loader 與功能裡（例如 1.40.0 的舊專案補
`stagePrompts`）。建議在 `lib/stores.js` 加 `schemaVersion` 與一組依序執行的 migration，
新增欄位時只需補一個 migration 與一個測試。

**另外，`lib/dataDir.js` 的 `writeJSONSafe` 是直接 `fs.writeFileSync` 覆寫原檔（已檢查程式碼）**，
寫到一半當機或斷電會留下被截斷的 JSON，且沒有備份可還原。改成「寫暫存檔 → `renameSync`」
並保留上一份 `.bak`，是成本最低、收益最直接的資料保護，建議跟 §2.3 一起在 `1.41.0` 做，
並補一個測試（模擬寫入失敗時原檔不被破壞）。

### P2：產品面

#### 2.9 已規劃的功能 A～D

見 `docs/parallel-dev/`。其中 B（托盤專案區塊的顯示條件）直接解決一個使用者會遇到的困惑：
從範本建立的專案任務預設未指派，托盤的專案區塊因此一開始是空的。

#### 2.10 提示詞變數與使用紀錄

- 提示詞支援 `{{主題}}`、`{{語言}}` 這類具名變數：複製時彈出小表單填值（專案階段流程已有
  「自動帶入主題與前面步驟的產出」，可沿用同一套組合邏輯）。
- 記錄使用次數與最近使用，知識庫排序可選「常用」。與功能 D 的「最近使用」共用資料。

#### 2.11 對話庫與知識庫打通

對話庫的一段好回答可「存為提示詞／範本」，或把對話內容送進專案某個步驟的產出欄位。
目前這三個模組各自獨立，只有文件庫能互相關聯。

#### 2.12 備份自動化

目前備份是手動匯出／匯入。可加「每週自動備份到使用者指定資料夾、保留最近 N 份」。
仍遵守原則：備份不含 cookie／localStorage／token。

#### 2.13 選擇器維護成本

各平台改版會讓 selector 失效，現有「測試擷取」可以診斷但要使用者自己修。建議支援匯入／匯出
單一平台的 selector 設定檔（使用者手動匯入，不自動從網路更新，符合核心原則），
並在擷取結果為 0 則時直接提示「可能是 selector 失效，點此開啟測試擷取」。

## 3. 關於「大改版」

**不建議整個改寫成前端框架（Vue／React＋Vite）。** 理由：目前無建置流程是這個專案的優點
（任何人改完 `npm start` 就能看到結果、AI 接續開發也不必處理建置設定）；痛點其實是少數超大檔案，
用 ES module 拆分就能解決。

建議的中間路線，依序判斷是否需要往下一步：

1. 先做 §2.7 的 ES module 拆分。
2. 若之後有 3 個以上畫面需要共用元件與狀態，再評估無建置的輕量方案（例如 Preact＋htm，
   以 vendor 方式放進 `renderer/vendor/`，與現有 pdf.js 的做法一致）。
3. 只有在 1、2 都做了、仍然難以維護時，才評估引入 Vite 等建置工具。

## 5. 這份建議的限制

- 沒有在真實 Electron 環境執行過 App，所有關於畫面行為的判斷都來自讀程式碼與文件。
- 本次整理的環境無法連到 npm 套件庫，因此沒有跑 `npm run lint`、`npm run format:check`，
  也沒有安裝 `sql.js`／`mammoth`；能驗證的部分（語法檢查、不依賴外部套件的測試、三語系鍵
  一致性、內建資料數量）已驗證。
- Electron 版本支援範圍會隨時間變動，升級前請以 Electron 官方的支援版本表為準。
