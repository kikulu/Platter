## このプロジェクトを作った理由

Claude、ChatGPT、Gemini、Grok を一日中行き来していると、ブラウザタブが
山積みになり、アカウントが勝手にログアウトし合い、以前保存したプロンプト
も見つからなくなります。このアプリはまさにその問題を解決するために作り
ました：

- 各アカウントは完全に独立したログインセッション（同じブラウザタブで
  アカウントを切り替えるのとは違い）で、Cookie を共有しません
- サイドバーからワンクリックで瞬時に切り替え、再ログイン不要
- 残しておきたい会話は手動で Markdown / JSON にエクスポート
- よく使うプロンプトや skill テンプレートを一箇所にまとめて管理、毎回
  打ち直す必要なし

**やらないこと**も明確です（詳しくは[設計原則](#設計原則)を参照）：
どのプラットフォームの非公開 API も呼び出さない、不正利用検知を回避する
自動化を行わない、ログイン情報をバックアップファイルに含めない。

## 使い方

1. アプリを起動し、サイドバーの「＋ アカウント追加」をクリック。
   プラットフォーム（Claude/ChatGPT/Gemini/Grok）を選び、任意の名前を
   付けて、開いたウィンドウで通常どおりログインします。
2. サイドバーのアカウント一覧をクリックすると切り替わります。手順 1 を
   繰り返せばアカウントを追加できます。
3. 会話をエクスポートするには：該当アカウントに切り替え、「現在の会話を
   エクスポート」をクリックし、Markdown か JSON を選択します。初回は
   「設定 → セレクタ設定」の要素ピッカーツールで調整しておくことを
   おすすめします（後述）。そうしないと内容が取得できないことがあります。
4. よく使うプロンプトは「ナレッジベース」に保存しておけば、コピー＆
   ペーストするだけで済み、毎回打ち直す必要がありません。組み込みの
   「企業ロールテンプレート」（HR／マーケティング／営業／カスタマー
   サポート／PM／エンジニア／財務／経営層）はすでにシステムプロンプト
   とユーザープロンプトに分割済みです。アカウントのロールを対応する
   職務に設定すれば、サイドバーの「デフォルトプロンプト」からそれぞれ
   個別にコピーできます（例：システムプロンプトは ChatGPT の Custom
   Instructions へ、ユーザープロンプトは会話入力欄へ）。複数手順の
   作業（論文執筆、研究計画、プロジェクト進行など）には「セット」が
   使えます。ステージ分けセットを 6 組内蔵しており（仕様駆動開発 SDD：原則 → 仕様 → 計画 → タスク → 実装を含む）、セットエディタで
   「＋ ステージ」から見出しを追加し、↑↓ で手順を別のステージへ移動
   できます。各ステージで「このステージをコピー」を押せばそのステージの
   プロンプトをまとめてコピーでき、手順の先頭のチェックボックスで進捗を
   管理できます。
5. 「設定」では、言語の変更、設定ファイルの保存フォルダの変更、拡張機能
   のインストール、設定一式のバックアップ／復元ができます。

## 設計原則

以下の 3 つの原則がこのプロジェクトのすべての技術的判断を貫いており、
新機能はまずこの基準をクリアする必要があります：

1. **どのプラットフォームの非公開・内部 API も呼び出さない**、不正利用
   検知を回避する自動化も行わない。会話のエクスポートは「現在画面上に
   すでに描画されている DOM の内容」を読み取る方式で、ユーザーが手動で
   選択してコピーするのと同じ効果しか持たない。
2. **サイトの保護機構を回避する処理を一切行わない**——Chrome ウェブ
   ストアの拡張機能を自動でダウンロード・解凍したり、サードパーティ
   サイトのセキュリティヘッダーを剥がしたりしない。
3. **ログイン情報をどんな可搬ファイルにも含めない**——バックアップや
   エクスポートファイルに Cookie や localStorage が含まれることはなく、
   それらは常に Electron が管理する、OS のユーザーアカウントに紐づいた
   場所に留まる。

## アーキテクチャ

<summary>技術的な詳細を見る（セッション分離、マルチウィンドウ設計、i18n、要素ピッカーなど）</summary>

### セッション分離とアカウント管理

- 各アカウントは `session.fromPartition('persist:<accountId>')` で独立
  した partition を持ち、Cookie / LocalStorage / IndexedDB が互いに
  漏れることはありません。`persist:` プレフィックスにより partition の
  データがディスクに書き込まれ、アプリを再起動して同じ id を使えば同じ
  ログインセッションに再接続できます。
- アカウントの画面は `<iframe>` や `<webview>` ではなく、`WebContentsView`
  （Electron 30+ の API）をメインウィンドウの上に重ねて表示し、
  `setBounds()` で位置を、`setVisible()` で表示・非表示を切り替えます。
  そのためアカウントの切り替えは瞬時に行われます。
- **遅延読み込み**：起動時にはアカウントのメタデータだけを登録し、
  `WebContentsView` の実体は初めて `switchAccount()` でそのアカウントに
  切り替えたときに作成されます。アカウントが増えるほど、この差が起動時の
  リソース消費に効いてきます。遅延読み込みされたアカウントが初めて
  読み込まれる間は、読み込み中の表示が出ます。

### 独立ウィンドウのアーキテクチャ

「アカウント追加」「ナレッジベース」「設定」は、メインウィンドウ内に
重ねる HTML ダイアログではなく、それぞれ独立した `BrowserWindow`
（`parent: mainWindow`、**モーダルではない**）です——`WebContentsView` は
CSS の z-index を無視するネイティブレイヤーのため、ページ内ダイアログは
覆われたりキーボードフォーカスを奪われたりしやすく、一方でモーダル
ウィンドウはメインウィンドウをロックしてしまい、要素ピッカーのように
メインウィンドウとの対話が必要な機能と衝突します。3 つのウィンドウは
同じ `preload.js` を共有し、`main.js` の `openChildWindow()` がそれらを
開く共通のヘルパーです。

### 多言語対応

`renderer/locales/` 以下の JSON 言語ファイルと、共通の
`renderer/i18n.js` ヘルパーが、`data-i18n` 系の HTML 属性を使って自動的に
翻訳を適用します。動的な文字列は `window.i18n.t(key, vars)` を使います。
言語設定は保存され、切り替え時にはすべてのウィンドウにブロードキャスト
されて同期します。

### 要素ピッカーツール

「設定 → セレクタ設定」では、DevTools を手動で開いて調べる代わりに、
画面上のメッセージを直接クリックして候補となる CSS セレクタを生成
できます——「例を選択：ユーザーのメッセージ」と「例を選択：AI の返信」を
それぞれ 1 回ずつクリックすると、アプリが両者を比較してメッセージ
コンテナのセレクタと、ユーザーメッセージを識別するためのキーワードを
割り出します。あくまで推測による最善の結果なので、適用後は確認し、
必要に応じて手動で調整してください。

### データの安全性

設定ファイルの書き込みはすべて共通の `writeJsonFile()` ヘルパーを
経由します：まず `.tmp` ファイルに書き込み、成功したら `rename` で
本番ファイルを上書きします（アトミック書き込み）。上書き前には既存の
ファイルを自動的に `.bak` としてバックアップします。インポート機能
（ナレッジベース、バックアップ）は事前に JSON の構造を検証し、形式が
合わない場合は明確なエラーメッセージを表示します。

## 開発

```bash
npm test          # ユニットテスト（純粋関数、データ層のシード、IPC ハンドラ、node:test、sql.js 以外の追加パッケージ不要）
npm run lint        # ESLint
npm run format      # Prettier による自動整形
```

`main.js` のモジュール化は完了しました。現在は App のライフサイクル
（単一インスタンスロック、`whenReady`、window-all-closed/activate）だけを
残した約 70 行のファイルです。データストア、ウィンドウ管理、会話の
キャプチャ/エクスポート、IPC ハンドラはすべて `lib/**` 以下に分割され
（IPC ハンドラはさらに業務領域ごとに `lib/ipc/` 以下へ分割）ています。
`lib/utils.js` には Electron API に依存しない純粋関数（文字列処理、
ファイルシステム関連のヘルパー）を置いており、分離することで
`node --test` で直接テストできます。各モジュールの役割分担と共有状態の
扱い方の慣例は `PROJECT_SPEC.md` の第 15 節「ファイル構成」を参照して
ください。

push / PR 時には [GitHub Actions](./.github/workflows/ci.yml) が構文
チェック・lint・ユニットテストを自動実行します——ただし実際に Electron
アプリを起動して操作するテストは含まれていない（CI 環境にはディスプレイ
がないため）ので、その部分は手動で `npm start` して確認する必要があり
ます。

## パッケージング

[electron-builder](https://www.electron.build/) でパッケージ化します：

```bash
npm run build:win     # Windows：NSIS インストーラー
npm run build:mac     # macOS：dmg
npm run build:linux   # Linux：AppImage
npm run build:dir     # インストーラーなし、動作確認用のフォルダのみ生成
```

出力先は `dist/`。アプリアイコンは `assets/icons/`（現時点では空）に
配置します。準備手順は
[`assets/icons/README.md`](./assets/icons/README.md) と
[`assets/ICON_PROMPTS.md`](./assets/ICON_PROMPTS.md) を参照してください
——アイコンを用意するまでは、アイコンファイルが見つからずパッケージング
に失敗しますが、これは想定どおりの動作です。

```
│   ├── default-knowledge-base.json # 組み込みプロンプトテンプレート48個（一般32個＋ロール別16個）＋ステージ分けセット6組
│   └── default-roles.json     # 組み込み企業ロール8種（初回起動時にロール一覧の初期値になる）
├── renderer/
│   ├── index.html / renderer.js / renderer.css   # メインウィンドウ

```

## 設定ファイルの保存場所

実行時に `app.getPath('userData')` 以下に自動生成されます：

```
config-location.json   # ポインタファイル：実際の設定フォルダの場所を記録
app-state.json          # アカウント一覧、選択中のアカウント、サイドバーの状態、デフォルトのエクスポート先、言語
knowledge-base.json     # ナレッジベースの項目
selectors.json          # 会話キャプチャに使うセレクタ
extensions.json         # インストール済み拡張機能の一覧
```

「設定 → 設定ファイルの保存場所」から、上記のうち `config-location.json`
を除くファイルを外部フォルダ（クラウド同期フォルダなど、複数マシンで
同じ設定を共有する場合など）に切り替えられます。実際のログイン用
Cookie・localStorage は**含まれません**。

## コントリビューション

フォークして PR を送っていただけます。PR を送る前に以下を確認して
ください：

1. `npm test` がすべて通ること
2. `npm run lint` で新たなエラーが出ていないこと
3. 動作に関わる変更については、実際に `npm start` で一通り動作確認して
   から提出すること（CI には Electron の操作テストは含まれません）
4. 上記の[設計原則](#設計原則)の 3 つ（非公開 API の呼び出し、サイトの
   保護機構の回避、ログイン情報をバックアップに含めること）に反する
   新機能は受け付けられません
